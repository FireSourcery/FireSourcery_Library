Literature survey · 22 Nov 2026 · Docs/Principles/StructSemantics.md

Shape is old prior art. The kinds are new.

StructSemantics.md says a struct is the shape of memory and its kind is the meaning wrapped around it. The split was in print between 1972 and 1989, and four languages and one kernel checker made “same shape, different type” a rule. The sources reviewed do not state the operational half: eight kinds of C struct defined by who writes them, when, where they live and how they are passed, with the kind fixing storage, passing form and API at the type. AUTOSAR comes closest. It attaches the kind to the role a data item plays and keeps one type across kinds.

The statement, marked against the literature

A struct defines the shape of memory; the module around it defines what the struct means. Each struct has a kind, set by its purpose and access pattern: who writes it, when, where it lives and how it is passed. The kind, not the shape, decides its storage, its passing form and its API. Two structs of one shape in different kinds are different types.

ClauseA struct defines the shape of memory; the module around it defines what the struct means.

Representation and meaning were split by 1985

Cardelli and Wegner open their survey with this clause: memory is an untyped universe of bit strings, and its meaning comes from outside. C's own standard says the same in normative text. Parnas puts the meaning in one module, and Simonyi says a structure's operations are independent of the fields that determine its representation. Cardelli and Wegner's vocabulary runs the other way. For them the type is the armour, while in the principle the struct is the bare representation and the module is the armour. The structure of the claim is the same.

The meaning of a piece of memory is critically determined by an external interpretation of its contents.
Cardelli & Wegner 1985, §1.1, reprint p. 3
A type may be viewed as a set of clothes (or a suit of armor) that protects an underlying untyped representation from arbitrary or unintended use
Cardelli & Wegner 1985, §1.2, p. 3
The meaning of a value stored in an object or returned by a function is determined by the type of the expression used to access it
ISO C11, N1570 §6.2.5p1
the invariant property of data structure, the set of operations in which the constructions participate, seems to be largely independent of the fields of the structure that determine only the representation
Simonyi, “Hungarian Notation”, Naming Rules, MSDN reprint 1999
A data structure, its internal linkings, accessing procedures and modifying procedures are part of a single module.
Parnas 1972, CACM 15(12), p. 1056
Property mismatches that have their cause in conflicts of the conceptual interface models cannot be resolved by connection systems but require human intervention
Kopetz, IFAC 2002, §3.4

The principle departs from the classic line in one place. Parnas, Liskov and Zilles, and Cook assume the owning module hides the representation, and Cook names the C idiom of a struct forward-declared in the header (Cook 2009, §2.3). Three of the principle's kinds (value, data model and packet) keep the shape public because the data is the interface. Their precedent is the data-description languages. PADS lets analysts “describe the physical layout of their data, as it is”. DataScript says “no attempt is made to hide such details from the programmer”. EverParse3D (§1.1) names the C habit of casting a byte array to a packed struct. In Reynolds's terms, the principle is extrinsic about bytes and intrinsic about meaning.

ClauseTwo structs of one shape in different kinds are different types.

Same shape, different type is a rule in four languages and a kernel checker

Morris gave the earliest clear statement in 1973. Ada 83, Modula-3 brands, Haskell newtype and GHC roles made it mechanical, and sparse checks it on plain C. C already gives two struct tags two distinct types (C11 §6.7.2.3p5), so it supplies the mechanism. It gives no criterion for when to declare the second tag. The principle supplies the criterion.

as intervals or as common, ordinary pairs, which they obviously are? Most people would agree that he should do the former and would regard as a type violation anything assuming the latter
Morris 1973, “Protection in Programming Languages”, §5, p. 17
Two type definitions always define two distinct types, even if they are textually identical
Ada 83 LRM §3.3
Brands distinguish types that would otherwise be the same; they have no other semantic effect
Modula-3 reference, DEC SRC
this distinction cannot be made by the compiler; it can only be specified by the programmer
Breitner, Eisenberg, Peyton Jones & Weirich, ICFP 2014, pp. 4–5
Each typedef creates a type of it's own, and will thus create a bitwise type that is not compatible with anything else
Torvalds on sparse, Sep 2004 (spelling as posted)
have the same existential type … points out a deficiency in the SOL typing discipline
Mitchell & Plotkin, TOPLAS 1988, pp. 483–484, on stacks and queues

A test for when

Simonyi's type calculus asks: “could the same set of operations be meaningfully applied to the quantities in questions? If so, the types are thought to be the same”. Applied to the principle's own example, a config is persisted and written by the user, while an AngleCounter_Ref_T bundle is rebuilt at Init and never persisted. The operation sets differ, so the types differ even when the fields match.

The limit: names are not type safety

“On its own, a newtype is just a name. And names are not type safety.” A name-only distinction holds through the “home module”, “a trust boundary where internal invariants are enforced by restricting clients to a safe API”. And: “If a newtype is completely transparent, and it is routinely wrapped and unwrapped at will, it is likely not very helpful.” (King 2020)

For C this means a second tag gets compile-time non-interchangeability, while each kind's write rule stays a convention inside its module. Simonyi conceded the same in 1999: “If a quantity is incorrectly classified, we have a style problem, not a bug.”

Counter-positions

Barr, BARR-C:2018 §5.1

Reuses one register-layout type on purpose: “this same type could then be used to create a shadow copy of the timer registers” (p. 33).

Hickey, 2011–2012

“Don't feel like I have to write a class now because I have a new piece of information. That's just silly.” His target is garbage-collected information systems.

Sharvit, 2022

Principle #2, “Representing data with generic data structures”.

Physical subtyping

C practice relies on layout prefixes (Siff et al. 1999; Chandra & Reps 1999, metadata only). The standard sanctions it only through the common initial sequence rule, §6.5.2.3p6.

None of these says meaning lives in the shape. They argue from convenience and reuse, and the disagreement is only about whether to name separate types. Modula-3's structural default and the GHC role design, which “generated vigorous debate” before choosing permissive defaults, sit on the same side.

The converse case the principle does not state

One meaning can take several shapes. Ada models it as distinct types joined by explicit conversion: “PACKED_DESCRIPTOR and DESCRIPTOR are two different types with identical characteristics, apart from their representation” (Ada 83 LRM §13.6). AUTOSAR notes that one physical value “might look very different when sent over CAN” (TPS_SWCT_01235), and Kopetz writes that “the semantic content of a variable is invariant to a change in representation” (2011, §2.2.4). The principle's packet and data-model kinds carrying the same information are this case.

Morris adds that “representation can be a multilevel affair” (§5, p. 18): a routine that prints pairs “is unconcerned with all but the pair tag”. Serialisers, DMA and debuggers may see only the shape layer of a struct that also has a kind.

Standards classify by access pattern; type theory does not

Type theory names the criterion only in general. Cardelli and Wegner say types “categorize objects according to their usage and behavior” (§1.1). Design guides sort aggregates on one axis at a time, mostly the invariant: C++ Core Guidelines C.2, and Stroustrup's “if and only if you can consider an invariant” (Artima 2003). The principle's runtime-model kind sits on that axis. Industrial standards use all four of the principle's axes, each attached to an instance or a declaration.

Who writes it

AUTOSAR TPS_SWCT_01266VariableDataPrototypes “are changed by the application software at runtime”; ParameterDataPrototypes “are constant (except for calibration access)”.

Where it lives

AUTOSAR MemMap §7.2.1.2“two different kinds of constants”: CONFIG_DATA for configurable behaviour, CONST for fixed values.
AUTOSAR Table 5.46swImplPolicy const “can be applied for parameters (not for those in NVRAM)”.
sparse __iomemComplain “if the pointer is ever dereferenced”; it lives in “address space 2”.

How it is passed or consumed

Kopetz 2002 §3.3State information needs “an update-in-place and a non-consumable read”; event information is “queued on sending and consumed on reading”.
AUTOSAR RTE §5.6.4–5.6.5Rte_Write for data semantics, Rte_Send for event semantics.
Diatchki & Jones 2006 §2.1A memory area “cannot be used directly as a function argument or result”, only by reference or pointer.

The principle's Derived (Ref) kind has three ancestors: AUTOSAR's derived configuration parameters, Cunningham's Visible Implication pattern (“Compute derived or redundant quantities implied by those already entered”, CHECKS 1994), and King's statement of the risk the Init-only rule manages: “Duplicating the same data in multiple places introduces a trivially representable illegal state: the places getting out of sync” (King 2019).

ClauseThe kind, not the shape, decides its storage, its passing form and its API.

AUTOSAR lets the kind choose all three, on the role

AUTOSAR Classic R22-11 is the only source reviewed that does all three by data kind.

Storage

SwAddrMethod and its MemorySectionType (“the essential nature of the data”) pick the MemMap section: VAR_INIT, VAR_CLEARED, CONST, CALIB, CONFIG_DATA_PREBUILD, CONFIG_DATA_POSTBUILD. Variables set later by an initialization routine still go in INIT or CLEARED.

SWCT Table 5.92–5.94 · MemMap p. 26–31

Passing form

Post-build configuration “shall be defined in a structure” in a separate segment, and is passed to <Mip>_Init() “via a const-qualified function parameter”.

SWS_BSW_00057, SWS_BSW_00160, §10.2.5

API

Rte_Write or Rte_Send by swImplPolicy, Rte_Pim for per-instance memory, Rte_Prm and Rte_CData for parameters, where “Access is read-only”.

SWS_RTE §5.6.4–5.6.17

StructSemantics.md: the kind is on the type

C keeps the two tags apart (§6.7.2.3p5). The type name shows the kind at every use.

AUTOSAR: the kind is on the role

One type; the structure is fixed and the policy is set per prototype.

the properties covering the structure shall not be redefined on DataPrototype. Implementation policy, semantics and code generation policy may be changed under consideration of compatibility rules
AUTOSAR TPS SWCT R22-11, TPS_SWCT_01273, pp. 346–347
the specific context gives the otherwise generic VariableDataPrototype a dedicated semantics
AUTOSAR TPS SWCT R22-11, Table 5.33, pp. 319–320

So AUTOSAR's rule is “different kind, different role”, a weaker rule than the principle's “different type”. Simulink, IEC 61131-3 and A2L also put the kind on the instance. AUTOSAR can do this because a generator carries the role to every use site: the RTE emits Rte_Prm or Rte_Pim, and MemMap emits the section. Plain C has no generator, so the type name is the one place a reader sees the kind at every use. This argument for binding the kind to the type is this survey's inference. Its cost, which AUTOSAR avoids, is duplicate same-shape types and the conversions between them.

The principle's own runtime-configuration row already follows the instance view: one type lives in NVM and in a RAM working copy, which is AUTOSAR's romBlock and ramBlock pair. “The kind decides storage” therefore means a storage plan that can name two places for one type.

Passing form fixed at the type, outside AUTOSAR

logically represents a single value, similar to primitive types … has an instance size under 16 bytes … is immutable
Framework Design Guidelines (Cwalina & Abrams 2008), when to choose a struct
References represent the modeling relation “knows about”; subobjects, as permitted by expanded types, represent the relation “has part”
eiffel.org; ECMA-367 §7.4
a struct that has elements that can reasonably be directly accessed should never be a typedef
Linux kernel coding style §5
even types with the same layout can still differ in how they are passed across function boundaries
Rust Reference, type layout

The C# guideline's 16-byte figure comes from copy cost; the principle's comes from AAPCS register passing. The AAPCS observation itself (structs over 4 bytes returned through memory unless inlined) has no counterpart in the sources reviewed.

ClauseNames carry the kind where a suffix exists.

Simonyi named the kind first, and Systems Hungarian shows how it decays

SIMONYI · 1976 THESIS, 1999 REPRINT

Type is the set of operations

Type is “determined by the set of operations that can be applied to a quantity”. “I recommend the use of a new tag for every new data structure”, and the tag “should also be used as the structure name in the program”.

→
SPOLSKY · 2005

The word “kind”

“I'm using the word kind on purpose, there, because Simonyi mistakenly used the word type in his paper, and generations of programmers misunderstood what he meant.” (Making Wrong Code Look Wrong)

→
SYSTEMS HUNGARIAN · THE DECAY

The prefix names the machine type

“the only thing that the prefix told you was the actual data type of the variable”, which Spolsky calls “a subtle but complete misunderstanding of Simonyi's intention”.

For the principle's suffixes the warning is concrete. A kind suffix stays useful while it names purpose and access pattern, and turns into Systems Hungarian once it names layout or storage section. Simonyi's TypeFromType conversion naming is a precedent for naming config-to-Ref builders.

You'll maybe call it personnel_record or mailing_address. At that stage you believe name and address are not just strings
Stroustrup, Artima 2003
a descriptive name that establishes a link between the chunk and its meaning helps human understanding
Kopetz, IFAC 2002, §3.4
the structure definition that defines the register layout
BARR-C:2018 §5.1, on timer_reg_t: a name chosen by layout

One terminology collision is worth a line in the document. In type theory “kind” already means the classifier of types, as in Diatchki and Jones's * against Area. Their Area is the one formal use that matches the principle's sense. No source reviewed uses “kind” for purpose or access-pattern classes of same-shape structs. That is a negative finding from limited search coverage.

What appears original

Within the sources reviewed, five things have no stated precedent.

  • The eight-way taxonomyOpaque state and transparent data as kinds of one aggregate. The members have separate ancestors; no source assembles them.
  • Kind defined by four operational axesType theory has only “usage and behavior”, and industry spreads the axes across separate attributes.
  • Kind as a type property in plain CWith no generator or checker. Stronger than AUTOSAR's “different role”.
  • One kind fixes storage, passing form and APIOutside AUTOSAR, precedents cover one or two of the three.
  • By value means static inlineThe platform rule drawn from AAPCS return conventions.

Edits to StructSemantics.md

Raised by the survey and applied to StructSemantics.md on 22 Nov 2026. The units item stays open there, with the prior art noted.

  • Source lineAdd Parnas 1972, Morris 1973, Cardelli and Wegner 1985 and Simonyi beside Evans, Fowler and Kopetz.
  • One type or twoSay when one type in two storage places is enough (the runtime-configuration row already does this) and when a second type is required: when the set of applicable operations differs, which is Simonyi's test.
  • What a type buysFor the transparent kinds a distinct type buys mix-up prevention. For the runtime model it buys write discipline, inside the home module only (King 2020).
  • Units, the open itemAUTOSAR and A2L keep the unit conversion as metadata and store the representation the code consumes. That favours _Pu in the struct, with user units shown by the protocol or app layer. This is an inference from the standards, not a rule they state.
  • The converse caseAdd one meaning in several shapes (packet and data model), which Ada §13.6 models as distinct types joined by explicit conversion.
